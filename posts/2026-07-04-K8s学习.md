## DNS

首先本地的dns服务器（根据返回，本地是100.125.0.1）会分析这个网址对应的ip，如果没有，那就向上一层级的dns服务器查询，直到查到那个ip为止（大学计算机网络课程）：

当 DNS 服务器（比如 `100.125.0.1`）在自己的 Map 里找不到 `www.bilibili.com` 时，它会开始一场**“向上问路”**的旅程。

#### 问“根服务器” (Root Server)：

- **100.125.0.1**：“大佬，你知道 `www.bilibili.com` 在哪吗？”
- **根服务器**：“我不知道具体的，但我知道 `.com` 归谁管。你去问 `.com` 的老大。”（返回顶级域 TLD 服务器地址）

#### 问“.com 服务器” (TLD Server)：

- **100.125.0.1**：“大佬，你知道 `bilibili.com` 在哪吗？”
- **顶级域服务器**：“我也不知道具体的，但我知道 `bilibili.com` 是在 **B 站自己的 DNS 服务器**上注册的。你去问它。”（返回权威 DNS 服务器地址）

#### 问“权威服务器” (Authoritative Server)：

- **100.125.0.1**：“兄弟，你是管 B 站的，`www.bilibili.com` 到底是谁？”
- **B 站权威服务器**：“拿好，它是 `a.w.bilicdn1.com`（CDN 地址）。”

#### 最后一步：

- **100.125.0.1** 很高兴，赶紧把这个结果**存进自己的 Map 里**（方便下次有人问时直接回答），然后把结果吐给你。

然后就获得了 `164.52.47.54`和 `164.52.44.50` 两个IP地址。



## CDN

在浏览器获得到两个IP地址后，随机选择一个，开始向他建立网络连接，并开始请求。

但其实这个也还依然不是B站服务器的真正地址，大部分情况下，他应该是**CDN服务器的地址**。CDN 的全称是 Content Delivery Network。它的核心逻辑是：**空间换时间**。通过在全球部署节点，CDN 把网站的静态内容缓存到离你物理距离最近的服务器上。在这个服务器上我们快速获得一些静态文件。比如首页的carousel之类的。

```
$ curl ipinfo.io/164.52.44.50
{
  "ip": "164.52.44.50",
  "city": "Seoul",
  "region": "Seoul",
  "country": "KR",
  "loc": "37.5660,126.9784",
  "org": "AS63199 CDS Global Cloud Co., Ltd",
  "postal": "03141",
  "timezone": "Asia/Seoul",
  "readme": "https://ipinfo.io/missingauth"
}%                                             
```

可以看到这个服务器在韩国首尔。



但是**所有的请求都是只到CDN而不请求真正的B站服务器吗**？一般有两种实现：

#### 传统的做法：动静分离（部分经过）

在几年前，很多 App 的做法是“分而治之”：

- **静态资源（走 CDN）**：比如 App 里的图标、广告图、短视频、背景音乐。这些流量会去 `cdn.example.com`。
  - 比例：占流量**体积（GB）的 90%** 以上。
- **动态 API（不走 CDN，直连）**：比如你的登录请求、发消息、查余额。这些请求会直接发往 `api.example.com`，而这个域名直接指向 **K8s 的负载均衡器 (LB)**。
  - 原因：以前觉得 CDN 只是个“缓存仓库”，动态数据反正不能缓存，绕一圈反而慢。



#### 现代的做法：全站加速 / 边缘代理（全部经过）

现在的大厂（比如字节、阿里、AWS、Cloudflare）更倾向于让**所有流量**都先经过 CDN 节点。

**为什么动态 API 也要走 CDN？（即使它不被缓存）**

1. **安全盾牌（WAF/DDoS）**：如果流量全走 CDN，你的 K8s 集群 IP 就可以隐藏起来。黑客攻击时，攻击的是 CDN 的数千个边缘节点，而不是你脆弱的单个机房入口。
2. **连接优化（TCP/TLS 握手）**：用户手机离 CDN 节点近。手机先跟 CDN 节点完成复杂的加密握手（很快），然后 CDN 节点通过**长连接专线**把请求传回 K8s。这比手机直接跨越半个中国连 K8s 要快得多。
3. **边缘计算**：有些简单的逻辑（比如判断用户地区、灰度发布）直接在 CDN 节点（边缘）就处理掉了，根本不需要进 K8s。



#### “经过”不代表“缓存”

这是用户最容易混淆的点：

- **图片/视频**：经过 CDN，**且留在** CDN（缓存命中）。K8s 根本不知道用户看了一张图。
- **登录/交易 API**：经过 CDN，但 **透传** 回 K8s（缓存穿透/不缓存）。CDN 只是充当了一个“高级快递员”和“保镖”。



#### 总结：用户 App 流量的百分比

如果从用户角度来看，流量分布大概是这样的：

| 流量类型                    | 是否经过 CDN      | 比例 (按次数计) | 比例 (按流量 GB 计) |
| :-------------------------- | :---------------- | :-------------- | :------------------ |
| 图片/视频/静态文件          | 是 (且被缓存)     | 约 70%          | 约 95%              |
| 业务 API (登录/下单)        | 是 (作为代理透传) | 约 30%          | 约 5%               |
| 特殊流量 (WebSocket/长连接) | 可能不经过        | 极小            | 极小                |



到这里，一个普通用户的权限就结束了。接下来从CDN到服务器是如何连接以及配置的，就必须要开发以及管理人员来决定了。比如连接AWS，或者一些负载均衡。

## 负载均衡器

经过CDN的未被缓存的流量开始请求一个负载均衡器。负载均衡器（Load Balancer）通常是云厂商提供的（如 AWS ELB, 阿里云 SLB）或者是公司自建的。对于 K8s 集群来说，这个请求接下来会经历以下旅程：



##### 1. 流量的入口：Ingress 与 Service

在 K8s 的世界里，请求首先会到达 **Ingress Controller**（比如 Nginx Ingress）。它像是一个高级的“分拣员”，根据域名和路径，把请求转发到对应的 **Service** 上。

而 Service 则是 Pod 的逻辑分组，它通过 **iptables** 或 **IPVS** 规则，将流量最终导向真正干活的容器——**Pod**。

那么问题来了：**K8s 是如何管理这些成百上千的 Pod，并确保它们在挂掉后能自动重启、在流量大时能自动扩容的呢？**

这就涉及到了 K8s 的“大脑”与“手脚”——**控制平面（Control Plane）\**与\**工作节点（Worker Nodes）**。



##### 2. K8s 的大脑：控制平面 (Control Plane)

控制平面负责集群的决策（如调度）以及检测和响应集群事件。它主要由以下几个核心组件组成：

- **API Server (集群的唯一入口)**：
  它是整个集群的“网关”。无论是通过 `kubectl` 命令行，还是内部组件之间的通信，都要经过它。它是唯一一个直接与数据库通信的组件。
- **etcd (集群的记忆体)**：
  这是一个高可用的键值数据库，存储了集群所有的状态数据。你可以把它理解为 K8s 的“笔记本”，记录了哪个 Pod 跑在哪个节点上，期望的副本数是多少等。
- **Scheduler (调度器)**：
  当你要创建一个新 Pod 时，Scheduler 会观察集群中各个节点的资源情况（CPU、内存），然后选出一个最合适的节点把 Pod 塞进去。
- **Controller Manager (控制器管理器)**：
  它是集群的“管家”。它负责维持集群的状态。比如，如果你定义了要运行 3 个 Pod 副本，结果有一个坏了，Controller Manager 就会发现这个偏差，并通知 API Server 去创建一个新的，以达到“最终一致性”。



##### 3. K8s 的手脚：工作节点 (Worker Nodes)

如果说控制平面是办公室里的管理层，那么 Worker Nodes 就是工厂里的一线员工。

- **Kubelet (节点代理)**：
  它是运行在每个节点上的“小队长”。它负责监听 API Server 分配给该节点的任务，并管理容器的生命周期。它会确保容器按照预期的状态运行。
- **Kube-proxy (网络代理)**：
  它负责处理节点的网络规则，实现我们前面提到的 Service 负载均衡逻辑。它确保无论 Pod 怎么漂移，流量都能正确找到它。
- **Container Runtime (容器运行时)**：
  这是真正运行容器的软件，比如 **containerd** 或 **Docker**。K8s 本身并不运行容器，它通过 CRI（容器运行时接口）调用这些工具来拉取镜像、启动容器。



##### 4. 回到那个面试题：架构如何协同？

当我们理解了架构，再看“输入网址”的过程，其实是这样的协同：

1. **开发者**通过 `kubectl` 发送指令给 **API Server**，说“我要部署 3 个 Web 服务”。
2. **etcd** 记录下这个需求。
3. **Controller Manager** 发现当前运行数为 0，要求创建。
4. **Scheduler** 算出这 3 个 Pod 应该放在 Node A、B、C 上。
5. Node A、B、C 上的 **Kubelet** 收到命令，调用 **Container Runtime** 把容器跑起来。
6. **Kube-proxy** 更新网络规则。
7. **用户的请求**通过负载均衡器进入，经过 **Ingress** 和 **Service**，最终由 **Kube-proxy** 引导，精准地落在某个 Node 上的 **Pod** 里。
